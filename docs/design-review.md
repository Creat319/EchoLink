## 0. 目标与硬约束

| 项 | 值 |
| --- | --- |
| 用途 | Windows 电脑的系统声音，从安卓手机放出 |
| 传输路径 | USB 网络共享（主）/ Wi-Fi（备用，不承诺延迟） |
| 音频格式 | 48 kHz / 16 bit / 立体声，**裸 PCM 不压缩** |

| 目标延迟 | 端到端 50–70 ms 设计工作点，以浸泡 P99 为准 |
| 可靠性策略 | **不重传、不 ACK**；丢包补静音（带淡入淡出）保持时间线连续 |
| 实测 | **45 ms 平均**（共享模式）、3 小时不断音、两台设备均通过 |

## 1. PC 端（发送）

### 1.1 抓取
- WASAPI **事件驱动环回**（`LOOPBACK | EVENTCALLBACK`），自研 COM interop（NAudio 拿不到 `IAudioClient3`）
- 抓取线程 `AvSetMmThreadCharacteristics("Pro Audio")` + `timeBeginPeriod(1)`
- 热路径全在抓取线程内同步完成：格式转换 → 重采样 → 分包 → `sendto`，不排队/不分配/不加锁

### 1.2 保活流（关键机制）
环回在没程序出声时不产数据，所以额外起一条**渲染流**持续写静音。它同时干三件事：
1. 让环回持续有回调
2. **路径 B 载体**：用 `IAudioClient3::InitializeSharedAudioStream` 请求最小引擎周期
3. 测试音/点击声发生器（写进同一条流，声音必然经过真实混音路径）

顺序关键：**先起保活流，再起环回流**。反过来环回已按默认周期建好，拉不下来。

### 1.3 抓取粒度 = 引擎周期（实测结论）
环回是**按引擎周期成批投递**的，它自己不能协商周期，只能"蹭"端点已有的周期：

| 端点类型 | 最小周期 | 环回投递粒度 |
| --- | --- | --- |
| 板载 HD Audio（S/PDIF） | **2.67 ms**（128 帧） | 128 帧/回调 |
| VB-Cable / HDMI | 10 ms（480 帧） | 480 帧/回调 |

路径 A（`InitializeSharedAudioStream` + LOOPBACK）在三种端点上**全部失败** `0x88890021`，
所以小周期只能靠路径 B 间接获得。

### 1.4 重采样与打包
- 24 抽头 Kaiser(β=7) 窗 sinc，256 相位查表 + 相位插值，纯 push 模型
- **每次抓取回调结束就把缓冲里剩下的数据整包发出**（包长 = 抓取粒度，≤240 帧）
- `timestamp` = **真实发送时刻**（`sendto` 前的 QPC 微秒）

### 1.5 网络与寻址
单 socket 双向（绑 47811，发往 47810）；`SIO_UDP_CONNRESET` 关闭。
寻址：网卡评分（USB 共享关键字 +60 / 有网关 +25 / 无线 −10）→ 取默认网关 → 发真包探测锁定。

PC 端 CPU 实测：**21.6% 单核**（含 WPF 界面刷新），收端 1.56% 单核。

## 2. 手机端（接收）

### 2.1 播放
Oboe：`LowLatency` + `Exclusive`（失败退 `Shared`）+ I16 + 2ch + 48k + `Usage::Game`，三级开流链并记录每级错误码。
**Oboe 内部缓冲 = 2 个 burst**（AAudio 保证回调尺寸 ≤ burst），真机确认回调恰好 256 帧 = burst。
欠载时按逐个 burst 递增到 4。

### 2.2 环形缓冲
SPSC 无锁，左右声道各 `int16[16384]`（341 ms），绝对帧号寻址（帧 n → `n & 0x3FFF`）。

| 情况 | 处理 |
| --- | --- |
| 缺口 ≤200 ms | 补等长静音 + 两端各 1 ms 淡入淡出 |
| 缺口 >200 ms | 不补，重建时间线 + 重新垫水位 |
| `sampleCount` 落后 >200 ms | 判定发送端重启，清环重置 |
| 边界 | 整包落在已写区间且落后 ≤200 ms → 视为重复包丢弃 |

### 2.3 读侧
- **启动垫水位**：先输出静音、不消费，攒够 `target + 一个批次` 才开始读
- Catmull-Rom 三次插值
- **欠载**：输出静音且**不推进读位置**（样本事后不丢）
- **积压**：超过 `target + 3 burst` 才丢帧，带迟滞（回落到 `target + 1 burst` 解除）+ 2.5 ms 淡入

### 2.4 闭环（当前版本）
```
控制量 = 最近 1 秒内"回调水位最小值"的最小值（原生按回调统计，控制线程取 1s 窗口）
目标   = clamp(burst + 5 ms, 6, 60)     // PHJ110: 5.33 + 5 ≈ 10.33 ms
欠载   = 目标 += 1 burst（1 秒去抖）
涨 2 ms/周期，收 0.5 ms/周期
比率   = clamp(1 + 误差×5e-5, 1±0.001)，一阶低通 α=0.01（τ≈5s），斜率 ≤1e-5/周期
抖动 P99 = 只展示，不参与控制
```

**为什么控制最小值**：PC 成批投递 → 水位是锯齿。控均值必然高估半批（≈5 ms），
且 20 Hz 控制周期是 10 ms 批的整数倍，采样相位锁死在锯齿上，时钟漂移会出现慢拍。

**为什么目标里没有抖动 P99**：`P99 + 5` 会把 PC 侧批处理延迟重复计一次。

### 2.5 加固
① `onErrorAfterClose` 置标志由控制协程重开；② 看门狗 400 ms 不推进判停摆；③ 开流后核对实际参数；
④ 首连 1 kHz 测试音 + 人工确认；⑤ 路由事件按设备集合签名去重 + 2 s 限流。

## 3. 实测数据

### 3.1 PC 侧（本机 Windows 10 22H2）

| 指标 | S/PDIF（2.67 ms） | HDMI（10 ms） |
| --- | --- | --- |
| 包长 / 包率 | 128 帧 / 528 B / **373 包/秒** | 240 帧 / 976 B / 197 包/秒 |
| 到达间隔 P50/P90/P99 | **2.75 / 3.00 / 3.50 ms** | 0.75 / 10.25 / 10.25 ms |
| `\|dᵢ\|` P99（真实发送时刻） | **0.25 ms** | **0.25 ms** |
| `\|dᵢ\|` P99（旧名义时间戳） | 2.50 ms | 5.25 ms |

连续性：30 秒/90 秒检查零畸形、零序号跳变、零采样数跳变。5 分钟浸泡 60196 包零丢。

### 3.2 手机侧（PHJ110，共享模式）

| 指标 | 值 |
| --- | --- |
| burst | 256 帧（5.33 ms） |
| 独占 | **被拒**（两台设备都没拿到） |
| 回调帧数上限 | **256 = burst**（证伪"一次回调取整个缓冲"） |
| 端到端 | **平均 45 ms** |
| 长时 | **3 小时声音未中断**；第二台设备延迟相当 |
| 网络丢包 | 约 0.16% |

### 3.3 45 ms 的拆解

| 环节 | 量级 |
| --- | --- |
| PC 抓取 + 打包 + USB | ≈4 ms |
| 环水位 | ≈15 ms |
| **手机输出路径（Oboe + AudioFlinger + DAC）** | **≈26 ms** |

手机输出路径是最大单项，主要由**共享模式的 AudioFlinger 混音层**贡献。
水位从 15 压到 8 只省 7 ms；**拿不到独占，端到端难低于约 38 ms**。

注意：手机回报的 `输出延迟`（`calculateLatencyMillis`）**已包含 AudioFlinger**，
不能和"Oboe 缓冲大小"混为一谈。

## 4. 踩过的问题（按发现顺序，含根因）

这一节是给评审看"这套方案在真实环境里被什么咬过"。

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 诊断工具浸泡吞吐掉到 122 包/秒、1.7 万序号跳变 | 收包线程每包排序全部间隔 + 每包回一次状态包 | 定长直方图 + 100 ms 节流 + 4 MB 收缓冲 |
| 2 | 路径 A 全线失败 | 环回不支持 `InitializeSharedAudioStream`（`0x88890021`），三种端点一致 | 放弃路径 A，只用路径 B |
| 3 | "本机拿不到 <10 ms 周期" | **只测了虚拟卡和 HDMI**，漏了板载声卡 | 加 `periods` 只读探测，发现板载 2.67 ms |
| 4 | 手机端 2475 次欠载，水位恒 10.19 ms / 目标 22.17 | **目标水位形同虚设**：读端从第 0 帧就读，水位自然收敛到"刚好够一次回调" | 加启动垫水位 |
| 5 | 修完仍然欠载 | 我当时**同时改了垫水位和 4 burst**，无法归因 | 后续单独验证：4 burst 无必要，回调尺寸 ≤ burst |
| 6 | WPF 窗口不显示（进程活着，只有 482×227 小框） | `InvariantGlobalization=true` 让 WPF Binding 解析 `en-US` 抛异常 | 关闭 invariant；已写入 build.md |
| 7 | 界面部分文字是黑字压黑底 | Material Design 只给控件模板内文字设前景色，裸 `TextBlock` 仍是 WPF 默认黑 | 窗口级 `TextElement.Foreground` |
| 8 | 端到端"名义延迟"虚报 32 ms | 公式是 `引擎周期 + 抓取缓冲`，但每次回调都读空，缓冲不构成延迟 | 删掉该字段，改为实测值 |
| 9 | PC 重启后手机静默数分钟（丢包 0、水位 0、欠载爆增） | `sampleCount` 从 0 重新计数，被当成"旧包"全部丢弃 | 落后 >200 ms 判定发送端重启 |
| 10 | 手机界面的抖动 P99 是 5 ms 级，但链路很干净 | **名义时间戳**把 PC 成批投递延迟灌进了差分 | 改用真实发送时刻，P99 降到 0.25 ms |
| 11 | 目标水位偏高、闭环只在补漂移 | `P99 + 5` 把 PC 批处理延迟重复计一次；均值控制又高估半批 | 控制改窗口最小值，目标改 `burst + 5` |
| 12 | Oboe 缓冲被顶到 4 burst 且降不回来 | `maxCallbackGapMs` 是**整个会话的峰值**，记下了开流时 205 ms 的正常空档 | 新增"调度型间隔"统计：读后重置、跳过开流 1 s、忽略 >100 ms |
| 13 | 停顿型欠载后延迟被推高 | 欠载后**一律重垫水位**，但那类欠载数据只是晚到、环会自己补满 | 欠载后 50 ms 复查，仍低于目标一半才重垫 |
| 14 | 新 PC + 旧 APK = 完全没声音且无提示 | 变长包对 v1 接收端不兼容（全判畸形丢弃） | 协议版本升 2 作能力标记，PC 收到旧版显著告警 |
| 15 | 缓冲归属判断错误（我写反了） | 我以为"环水位挡回调迟到"；实际回调迟到时网络线程照常写环、环只会涨，被抽干的是 Oboe 缓冲 | 环挡数据到达停顿，Oboe 缓冲挡回调间隔 |
| 16 | 停顿归因结论无依据 | `d` 用真实发送时刻时 PC 停顿会在差分里抵消；且**接收端跑在同机**，混入了本机线程调度 | 增加"最大发送间隔"统计，真机两侧分开看 |

## 5. 当前可疑点 / 未解决

### 5.1 45 ms 里有 26 ms 在系统里，摸不到

两端都没拿到独占，共享模式必经 AudioFlinger 混音，这段延迟不可见、不可控。

**评审纠正了我两处误解**（已采纳）：

- `AudioStreamBuilder::setMMapPolicy()` 并不存在；存在的是 `OboeExtensions::setMMapEnabled()`，
  官方注明仅供测试，且只影响调用它的应用——它只决定"是否**允许**选 MMAP"，不能让不支持的设备变成支持
- "降到 AudioTrack"不是新路径：FAST 混音器同时服务 Java AudioTrack 和 AAudio，
  我们现在的共享模式本来就是带 FAST 标志的 AudioTrack

**已按建议做定性**（v0.2.1）：开流时记录三项 + 两个系统属性，写入 logcat 与 UI：

```
mmap: supported=? enabled=? used=? | props[policy=? exclusive=?]
```

判据：
- 两项支持位都为 false → 设备不提供，应用侧无解，**不再试 Usage 组合**
- 支持但 `used=false` → 落到普通混音器，去 logcat 搜 `FAST denied`（日志会列出采样率等字段）；
  普通混音器周期按 ≥20 ms 取整，这可能是 26 ms 偏大的原因（推测）

**仍要问：** 若 `used=false` 且 FAST 被拒，除了接受 26 ms 还有别的路吗？
（本机能否从应用侧影响 FAST 准入？还是只能靠设备/系统版本）

### 5.2 目标水位只涨不降 —— 已修，约 7 ms

原实现每次欠载固定 `+1 burst`，且**没有回落路径**。真机上目标从 10.3 ms 爬到 17.3 ms 后停住，
而那次欠载早已结束——等于白付 7 ms，比变长包省下的 2 ms 还多。

v0.2.1 改为**带衰减的棘轮**：

```
基线   = burst + 5 ms
棘轮  += 欠载缺口 + 2 ms，累计上限 +10 ms
保持    60 s（任何欠载重置计时）
衰减    0.1 ms/s，条件是"最小水位仍高于下限且无欠载"
```

顺带把评审提的"峰值模式 ≥2 次才抬"门槛去掉了——有衰减退场就不需要门槛。

**仍要问：**
- 这个方案是否等价于评审设想的峰值模式？有没有更稳的取法（如按欠载强度加权）？
- 60 s 保持 + 0.1 ms/s 的取值是否合理？水位回落本身受比率上限约束（±0.1% ≈ 1 ms/s），
  7 ms 至少要 7 s 才能落回来，衰减速度比这个还慢——是否该更快？

### 5.3 自动化延迟测量：只做了一半

v0.2.1 加了轨迹日志（见 5.7），但 `getTimestamp` 那条线**还没接**。
评审给的拆法是：`总延迟 ≈ PC 常量 + 链路抖动 d + 环水位 + 输出延迟`，前三项手机侧都有。

**仍要问：**
- `getTimestamp` 在共享模式下取 1 秒中位数，粒度误差大概多少？够不够看尾部？
- ping-pong 估钟差的必要性：只是为了把 PC 侧常量对齐进去？
  如果只关心**相对值**（趋势和尾部），是否根本不需要钟差？

### 5.4 变长包把包率推到 373/秒（WiFi 未实现）

延迟上是赚的（到达间隔 5.50 → 2.75 ms），但 WiFi 空口开销翻倍（每包一次仲裁 + ACK）。

评审建议：包长做成协商参数，USB 随抓取粒度、WiFi 合到 240 帧（5 ms / 960B，不超 MTU），
并同时持有两个 WifiLock（`LOW_LATENCY` 仅前台亮屏有效，息屏靠 `HIGH_PERF`）。

**状态：未实现**。理由：目前只有 USB 主路径，没有 WiFi 模式可挂。

### 5.5 无压缩的代价（此处我曾说错，已修正）

**我此前说"1.56 Mbit/s ≈ 700 MB/小时会吃掉流量套餐"——这是错的。**
USB 共享时音频包的目的地就是手机本机地址，在手机内部终结，**不会进蜂窝网络**；Wi-Fi 局域网同理。
真正的代价是**耗电**和**空口占用**。

而空口开销主要按**包数**算，所以 5 ms 的 960B PCM 包与 Opus 小包的空口时间差别不大（推断）。
Opus 的真正价值是 FEC/PLC 抗丢包，代价是至少多一个编码帧的延迟。

**修正后的结论**：Wi-Fi v1 先用同一套裸 PCM + 大水位 + 延后 5–10 ms 的独立副本
（约 3.1 Mbit/s，对 Wi-Fi 不算压力）；真机上 PCM 撑不住再考虑 Opus。

### 5.6 罕见停顿的预算 —— 已由 5.2 的棘轮覆盖

不再单列。棘轮本身就是"停顿后临时抬高、再慢慢退场"，不需要额外机制。

### 5.7 收敛判据：日志已就位，阈值待确认

v0.2.1 起每 10 秒写一行 CSV（应用私有目录 `files/logs/trace-*.csv`）：
秒、最小水位、均值水位、比率、目标、Oboe burst、欠载累计、输出延迟、调度间隔峰值。

评审给的候选判据（需标定）：

- 水位最小值：10–30 分钟窗口回归斜率 < 0.2 ms/min（≈3 ppm），峰峰值 < 2 ms
- 比率：相邻 10 分钟窗口稳态均值变化 < 10 ppm，且 `|ratio−1|` 小于上限的一半
- 目标与 Oboe 缓冲热机后不再上涨；欠载 ≤ 1 次/10 分钟

**仍要问：** 这几条阈值是按经验给的还是可以推导？如果 3 小时后比率仍贴着 ±0.1% 的一半以上，
优先怀疑什么（漂移超预期 vs 控制量有偏差）？

### 5.8 干扰场景没测

评审给的优先级（已采纳，尚未执行）：

1. PC 端游戏/视频的 CPU + GPU 负载（真实场景，最可能放大 PC 侧停顿）
2. 息屏/锁屏 ≥30 分钟（厂商省电策略可能杀前台服务或降频）
3. 手机 CPU 满载 / 发热降频（看回调间隔与 Oboe 缓冲）
4. 同一 USB 链路上跑大流量（并检查 `route print`，别让 PC 上网流量默认走手机）
5. 蓝牙/耳机插拔（路由切换，属功能测试）

## 6. 明确的非目标

- 不做重传/ARQ（引入不确定性延迟）
- 不做 PC↔手机钟差同步（差分已够用，除非上 DLL）
- 不做音画同步（纯音频场景）
- 不做多设备同时播放（需要广播 + 各自独立闭环）
