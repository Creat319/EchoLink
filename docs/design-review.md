# EchoLink 实现说明与待评审问题

> 本文是给外部评审者的技术说明：当前怎么实现、实测到什么、哪里可疑。
> 目标是**找方案层面的改进**，不是代码风格。
> 线格式权威定义见 [protocol.md](protocol.md)，设计取舍见 [architecture.md](architecture.md)，实测数据见 [verification.md](verification.md)。

## 0. 目标与硬约束

| 项 | 值 |
| --- | --- |
| 用途 | Windows 电脑的系统声音，从安卓手机放出 |
| 传输路径 | USB 网络共享（主）/ Wi-Fi（备用，不承诺延迟） |
| 音频格式 | 48 kHz / 16 bit / 立体声，裸 PCM |
| 分包 | 240 帧 = 5 ms = 976 B（16 B 头 + 960 B 载荷），200 包/秒 ≈ 1.56 Mbit/s |
| 目标延迟 | 端到端 50–70 ms，**以浸泡测试 P99 为准，不看均值** |
| 可靠性策略 | **不重传、不 ACK**。丢包补静音保持时间线连续，稳定性靠自适应水位闭环 |
| 依赖 | PC: C#/.NET 8 + NAudio；手机: Kotlin + Compose + Oboe (C++/NDK) |

包头：`seq:u32 | sampleCount:u64（本包首帧绝对帧号）| timestamp:u32（微秒）| PCM:960B`

## 1. PC 端（发送）

### 1.1 抓取
- WASAPI **事件驱动环回**（`AUDCLNT_STREAMFLAGS_LOOPBACK | EVENTCALLBACK`），自研 COM interop
  （NAudio 只封装到 `IAudioClient`，拿不到 `IAudioClient3`）。
- 抓取线程 `AvSetMmThreadCharacteristics("Pro Audio")` + `timeBeginPeriod(1)`。
- 整条热路径挤在抓取线程里同步完成：格式转换 → 重采样 → 分包 → `sendto`。**不排队、不分配、不加锁**。

### 1.2 保活流
环回在没程序出声时不产数据。起一条**渲染流**持续往同一端点写静音，让环回持续收到回调。
这条流同时承担两个职责：
- **路径 B 载体**：用 `IAudioClient3::InitializeSharedAudioStream` 请求最小周期，试图间接拉低环回的引擎周期；
- **测试音/点击声发生器**：写进同一条流，声音必然经过设备混音与环回路径，能真实验证全链路。

顺序很关键：先起保活流，再起环回流（否则环回流已按默认周期建好）。

### 1.3 重采样
设备率 → 48 kHz：24 抽头 Kaiser(β=7) 窗 sinc，256 相位查表 + 相位间线性插值，
每相位归一化（保证直流增益 1），降采样时截止频率按比例收缩。纯 push/pull 原地处理
（不用 NAudio 的 pull 模型，为了少一条线程、少一层缓冲）。

### 1.4 分包与时间戳
凑满 240 帧发一个包。`timestamp` 用**名义时间**（`起点 + sampleCount×1000/48`），
不是真实抓取墙钟——因为接收端只做差分 `d_i = Δ到达 − Δ时间戳`，名义时轴等价于"到达间隔 − 5 ms"，
正好是要吸收的抖动，恒定偏移被差分消掉。

### 1.5 网络
单个 UDP socket 双向：绑定 47811，发往手机 47810；手机把 40 B 状态回报发回源地址:源端口。
`SIO_UDP_CONNRESET` 关闭，避免手机离线时 ICMP 让 `Receive` 抛异常。回报仅用于显示，音频链路不依赖它。

### 1.6 寻址
枚举网卡，按"USB 共享关键字 +60 / 有网关 +25 / 以太网 +10 / 无线 −10 / 虚拟剔除"评分，
取最高分的**默认网关**作为手机地址；再发真实音频包探测，1.2 s 内收到回报即锁定。不写死 IP。

## 2. 手机端（接收）

### 2.1 播放
Oboe：`LowLatency` + `Exclusive`（失败退 `Shared`）+ `I16` + 2ch + 48 kHz + `Usage::Game` + 数据回调。
开流按三级链尝试并打印每级错误码：独占@48k → 独占@设备原生率（`kUnspecified`）→ 共享@48k。
开流后核对实际参数，不一致报给 UI。

**Oboe 内部缓冲强制 ≥4 burst 且 ≥20 ms**（共享模式下 `setBufferCapacityInFrames(1024)` +
`setBufferSizeInFrames(max(4×burst, 20ms))`）。理由见 §4。

### 2.2 环形缓冲
SPSC 无锁，左右声道各 `int16[16384]`（341 ms）。**绝对帧号寻址**：帧 n 落槽 `n & 0x3FFF`。

写端（UDP 线程）处理：
| 情况 | 处理 |
| --- | --- |
| `ref > 期望`，缺口 ≤200 ms | 补等长静音 |
| `ref > 期望`，缺口 >200 ms | 不补，重建时间线 + 重新垫水位 |
| `ref < 期望`（小幅） | 视为重复/乱序，丢弃 |
| `ref < 期望`（落后 >200 ms） | 判定发送端重启，清环重置 |
| 环写满 | 丢本包 + 请求读端跳水位 |

### 2.3 读侧
- **启动垫水位**：开流/重建后先输出静音、**不消费**，攒够 target 帧才开始读（垫水位期间静音不计欠载）；
- 每输出帧按 `baseStep × ratio` 推进读位置，`baseStep = 48000/实际采样率`；
- Catmull-Rom 三次插值（`idx-1..idx+2`）；
- **欠载**：剩余帧输出静音且**不推进读位置**（样本事后不丢），靠比率慢慢拉回；
- **积压 >2× target** 才丢帧：读位置跳到 `写头 − target`，2.5 ms 淡入。

### 2.4 闭合环（核心）
控制协程 20 Hz，看门狗 4 Hz。参数：

| 参数 | 值 |
| --- | --- |
| 目标水位 | 起步 30 ms → 稳定后 `P99(|d|) + 5 ms`，clamp **[20, 60]** ms |
| 水位硬下限 | `max(20 ms, Oboe 缓冲 × 1.15)` |
| 欠载响应 | 立即 +1 burst |
| 上涨 / 收缩速率 | +2 ms / 0.5 ms 每 50 ms 周期 |
| 重采样比率 | `1 ± 0.001`，一阶低通 α=0.01（τ≈5 s），斜率 ≤1e-5/周期 |
| 预热 | 90 s 且 ≥600 遥测样本后才进入自适应 |

抖动定义：`d_i = (到达_i − 到达_{i−1}) − (时间戳_i − 时间戳_{i−1})`，
两端时钟不同源但做差分即可消掉偏置；`|d|` 进 0.25 ms 分桶直方图取 P99。

### 2.5 加固
① `onErrorAfterClose` 置标志 → 控制协程重开（不在回调里重开）；
② 看门狗比对回调计数，400 ms 不推进判停摆重开；
③ 开流后核对实际参数；
④ 首连播 1 kHz 测试音 + 用户确认（发现"静默重路由到蓝牙"的唯一手段）；
⑤ 路由事件按输出设备集合签名去重 + 2 s 限流（实测一次变化连发 12 条）。

## 3. 实测数据（Windows 10 22H2 + PHJ110，USB 共享）

### 3.1 PC 侧
| 指标 | 结果 |
| --- | --- |
| 路径 A（`InitializeSharedAudioStream` + LOOPBACK） | **失败 `0x88890021 AUDCLNT_E_INVALID_STREAM_FLAG`**，VB-Cable 与 HDMI 一致 |
| 路径 B（保活流请求最小周期） | 接口成功，但两端点 `min == default == 10 ms`，**没有更小周期可拿** |
| 环回投递粒度 | 每回调恰好 441 帧(44.1k) / 480 帧(48k) = **整周期成批** |
| 5 分钟浸泡 | 60196 包，畸形 0、序号跳变 0、累计采样数跳变 0、速率 199.7 包/秒 |
| 到达间隔 | P50 0.75 ms，P90/P99 10.25 ms，最大 72.9 ms |

### 3.2 手机侧（PHJ110）
| 指标 | 结果 |
| --- | --- |
| burst | 256 帧（5.33 ms） |
| 独占模式 | 未拿到，回退 Shared（失败码仍在收集） |
| 修复前 | 水位恒 **10.19 ms** / 目标 22.17 ms / 欠载 **2475 次**，每次只差约 15 帧(0.3 ms) |
| 修复后（垫水位 + 4 burst 缓冲） | 水位 **31 ms** / 目标 30 ms / 欠载 **0**（单次观测） |
| 网络丢包 | 约 0.16%（4 万包丢 65 个） |

## 4. 两个已定位的关键结论（调参依据）

1. **PC 端是成批投递的**：引擎周期 10 ms，包成组到达（P99 10.25 ms vs P50 0.75 ms）。
   所以手机端水位下限必须能跨过一个完整发包间隔，10 ms 下限必然周期性欠载。
2. **目标水位原先形同虚设**：消费端从第 0 帧就读，水位自然收敛到"刚好够一次回调"的临界值（≈10 ms），
   目标值只被用于比较、没有机制把真实水位垫起来。加入"启动垫水位"后才真正生效。

## 5. 我认为可疑、需要评审的地方

### 5.1 闭合环的稳定性（最关心）
当前是**对瞬时水位做一阶低通 + 斜率限幅**，没有积分项、没有累积样本数参与。
Adriaensen 指出过直接对水位取平均会有长期不收敛误差。请评估：

- 是否需要升级为「累计读写样本数 + 滤波后时间戳 + DLL」？
- 若维持一阶环，长期稳态误差的量级大概多少？在 ±0.1% 比率上限下能否收敛？
- 当前 τ≈5 s（α=0.01 @20 Hz）是否合适？更快会不会可闻？

### 5.2 两级缓冲的分配是否最优
手机侧现在是**串联两级**：环形缓冲水位 ≈24.5 ms + Oboe 缓冲 ≈21.3 ms ≈ **46 ms**，
再加 PC 侧 ≈10–15 ms，端到端约 60–75 ms。可疑点：

- Oboe 缓冲是否真需要 4 个 burst？若 AAudio 回调本身按 burst 粒度触发（≤5.33 ms），
  2 个 burst(10.7 ms) 是否就够？（怀疑点：若 AAudio 一次回调要 1024 帧，则 21 ms 是必需的）
- 更优分配是否是「水位大、Oboe 缓冲小」（如 20 + 10.7）而非「24.5 + 21.3」？
- 有没有办法把两级合成一级（例如让 Oboe 直接读我们的环、或反过来把环做薄）？

### 5.3 抖动指标是否成立
`d_i` 里混入了三件事：PC 成批投递、USB 链路、安卓调度。三者无法分离。
后果是 `P99 + 5 ms` 基本被 PC 的 10 ms 周期主导，目标水位顶到下限附近，
**闭环实际上只在做漂移补偿，水位维度没有多少调节余地**。请评估：

- 是否该把"PC 侧批处理延迟"作为已知常量单独剥离，只用剩余抖动算目标？
- 是否需要 PC 端提供真实的采集时刻（QPC）而不仅是名义时间戳，让接收端能区分？

### 5.4 欠载后的恢复太慢
欠载时补静音不推进读位置 → 延迟被推高，之后靠比率（τ≈5 s，上限 0.1%）慢慢抽干。
最坏要十几秒才回到目标。是否应该在欠载后采用更激进的恢复（临时提高比率上限 / 直接丢一段）？

### 5.5 丢包 0.16% 的处理
USB 链路实测有 0.16% 丢包，当前只能补静音（听到轻微断续）。带宽只有 1.56 Mbit/s，
USB 绰绰有余，是否值得做**简单冗余**（每包发两遍 / 奇偶校验包），代价 2× 带宽？

### 5.6 其他可动的地方
- 分包粒度：5 ms → 2.5 ms（400 包/秒）能否降低抖动、代价是包率翻倍？
- PC 端能否绕开 10 ms 引擎周期？已知本机 IAudioClient3 两条路径都拿不到，还有别的办法吗
  （例如独占模式抓取、进程环回 `ActivateAudioInterfaceAsync`、`AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`）？
- 是否该用 Oboe 自带的 `LatencyTuner` 替代自研水位控制？

## 6. 明确的非目标

- 不做 Opus/压缩（带宽非瓶颈）
- 不做重传/ARQ（会引入不确定性延迟）
- 不做 PC↔手机钟差同步（RTT/RTCP 式）（差分抖动已够用，除非要上 DLL）
- 不做音画同步（纯音频场景）

## 7. 评审结论与处置（评审后追加）

外部评审给出的意见里有三条**推翻了原来的结论**，已按证据处理：

| 评审意见 | 处置 | 证据 |
| --- | --- | --- |
| 4 个 burst 无依据，`numFrames ≤ burst` | 改为 2 burst，欠载时递增到 4 | AAudio 语义；`maxCallbackFrames` 暴露到 UI 可当场证伪 |
| 环水位 ≥ Oboe×1.15 无物理依据 | 解除耦合 | 两级缓冲吸收的是不同抖动源 |
| 控制量应为窗口最小值（防采样混叠） | 原生按回调取最小值，控制线程取 1 s 窗口 min | 见 §5.3 的混叠机制 |
| 时间戳改为真实发送时刻 | 已改 | `\|dᵢ\|` P99：HDMI 5.25 → 0.25 ms，S/PDIF 2.50 → 0.25 ms |
| 板载声卡可能给 2.67–3 ms | **实测成立** | S/PDIF `min 128f = 2.67 ms`，环回投递粒度随之从 480 帧降到 128 帧 |
| 需要 DLL | 结论：不需要 | 一阶环稳态误差 = 漂移/增益，20–100 ppm 下仅 0.2–1 ms |
| 别把两包塞进同一包（超 MTU） | 采纳；冗余方案暂不做 | 留待丢包定位后再议 |

仍未处理（需要真机数据）：丢包 0.16% 的冗余方案、进程环回（需 Win11）、虚拟声卡驱动（需签名）。
