# EchoLink 线格式规范 v1

本文件是 PC 发送端与 Android 接收端之间**唯一权威**的协议定义。两端的实现都必须与本文一致；
`pc/src/EchoLink.Core/Protocol/PacketFormat.cs` 与
`android/app/src/main/java/com/echolink/app/audio/Protocol.kt` 是它的两份可执行镜像，
`docs/verification.md` 中记录了两端逐字节核对的结果。

- 传输：UDP，单向为主（音频 PC → 手机），反向只有低频状态回报。
- 无重传、无 ACK、无拥塞控制。稳定性来自接收端自适应水位 + 微量重采样，不来自网络层。
- 所有整数均为**小端序（LE）**。
- 无加密、无握手。校验只做长度校验，不做 CRC（USB 网络共享链路上以太网 FCS 已由硬件保证）。

---

## 1. 基本参数

| 项 | 值 |
| --- | --- |
| 采样率 | 48000 Hz |
| 位深 | 16-bit signed PCM（LE） |
| 声道 | 2（交错，L,R） |
| 每包帧数 | **可变，1–240 帧**（上限 240 帧 = 5.000 ms） |
| 每包 PCM 字节 | 帧数 × 2 × 2 |
| 每包总字节 | 20 + 帧数 × 4（上限 **980 B**） |
| 包率 | **可变**：板载 2.67 ms 端点上 375 包/秒；10 ms 端点上是 200 包/秒 |
| 净荷码率 | 恒为 195.3125 KB/s ≈ 1.5625 Mbit/s（与包率无关） |
| 音频端口（手机监听） | **47810** |
| 回报端口（PC 监听） | **47811**（同时也是 PC 音频包的源端口，也是上行流的目的端口） |
| 上行流 | 单声道 int16 @48 kHz，每包 480 帧（10 ms / 960 B），`stream=1` |

PC 的发送 socket 绑定固定本地端口 47811，因此手机把回报包、上行音频包都发回
“收到音频包的源地址:源端口”即可回到 PC，不需要第二套端口协商。

## 2. 音频包（双向，20 + 帧数×4 B，上限 980 B）

```
偏移  大小        类型      字段          含义
0     4           u32       seq           每包 +1，2^32 回绕。仅用于丢包统计与乱序诊断
4     8           u64       sampleCount   本包首帧在“本次会话”内的绝对帧号，从 0 开始
12    4           u32       timestamp     本包发出时刻（微秒，发送端单调时钟低 32 位）
16    4           u32       stream        0 = 下行系统音频，1 = 上行麦克风（v3 起）
20    frames×B     i16[]     pcm           交错采样（下行 4 B/帧，上行 2 B/帧）
```

**包长可变**：PC 端每次抓取回调结束时把缓冲里剩余的数据整包发出，
所以包长等于抓取粒度（板载 2.67 ms 端点是 128 帧 = 532 B），
超过 240 帧时拆成多个整包。接收端**必须按数据报长度推导帧数**：

```
frames = (datagramBytes − 20) / bytesPerFrame     要求 > 0、整除，且 ≤ 240
```

要点：

- `sampleCount` 是接收端环形缓冲的写入锚点：帧 `n` 的环形位置 = `n & (ringFrames-1)`。
  接收端据此实现“缺失区间补静音、保持时间线连续、不等待重传”。
- `sampleCount` **每包递增的步长等于该包帧数**，不是固定 240。连续性检查必须用上一包的实际帧数，
  否则变长包会被误判成断流。
- `stream` 区分方向。PC 侧先按回报包（magic 校验）解析，失败再按音频包解析，
  两者长度域不同（40 B / ≥20 B），不会互相误判。
- `timestamp` 是**真实发送时刻**（`sendto` 前的 QPC），不是由 sampleCount 推导的名义时间。
  名义时间戳会让接收端的抖动差分把 PC 侧成批投递延迟也算进去（实测 HDMI 上多出 5 ms）。
- `seq` 与 `sampleCount` 之间存在冗余关系，接收端两者都统计，用于区分“网络丢包”与“发送端断流”。
- 载荷不是整帧、或超过 240 帧的包一律丢弃并计入 `malformed`。

## 3. 状态回报包（手机 → PC，40 B）

每 500 ms 一个；手机在收到每个音频包时把该包的源地址记为目标，回报发回同一地址+端口。

```
偏移  大小  类型   字段            含义
0     4     u32  magic           0x50524C45（内存中即 ASCII "ELRP"）
4     2     u16  version         1
6     2     u16  type            1 = 周期状态回报
8     4     u32  reportSeq       回报序号，每包 +1
12    8     u64  framesPlayed    自开流以来已交给音频设备的帧数
20    4     u32  packetsReceived 收到的合法音频包数
24    4     u32  packetsLost     按 seq/sampleCount 推算的丢包数
28    4     u32  underruns       欠载次数（数据回调取不到足够帧）
32    2     u16  waterMs         当前缓冲水位（毫秒，饱和截断）
34    2     u16  targetWaterMs   当前自适应目标水位（毫秒）
36    2     u16  jitterP99Us     到达间隔抖动 P99（微秒，饱和截断）
38    2     u16  latencyMs       输出延迟估计（毫秒，Oboe calculateLatencyMillis）
```

PC 侧收到回报后刷新“手机已连通”状态与统计面板；**音频链路不依赖回报**，
回报丢失不影响播放，也不触发重传。

## 4. 抖动与水位（接收端语义，供两端对齐）

对每个音频包 i，令

- `a_i` = 本地收包时刻（单调纳秒）
- `t_i` = 包头 `timestamp`（微秒）

则单跳抖动

```
d_i = (a_i - a_{i-1}) - (t_i - t_{i-1})
```

两个时钟域只是做**差分**，恒定的时钟偏置被消掉，剩下的是网络与调度抖动。
由于 `t_i` 是真实发送时刻，PC 侧的成批投递/线程停顿会同时放大 `Δa` 与 `Δt`、在差分里互相抵消，
所以 `d_i` 只反映 `sendto` 之后引入的延迟。`|d_i|` 目前**只用于展示与起停诊断**，
不再参与目标水位计算（控制量是水位窗口最小值，目标 = `burst + 5 ms`，见 architecture.md §4.2）。

## 5. 版本与兼容

音频包头没有 magic/version 字段。**包长可变之后也无法再用尺寸做隐式版本标识**，
所以帧数必须由长度推导（见 §2）；任何字段布局变更仍然必须换端口，避免老客户端误解析。

版本历史（指回报包的 `version` 字段）：

| 版本 | 变更 | 兼容性 |
| --- | --- | --- |
| 1 | 初版，音频包固定 240 帧 / 976 B | — |
| 2 | 音频包长度可变（跟随抓取粒度，1–240 帧） | **不兼容**：v1 接收端会把非 976 B 的包全判为 `malformed` 丢弃 |
| **3** | **包头加 `stream` 字段（头 20 B），新增上行麦克风流** | **不兼容 v1/v2**：老接收端按 16 B 头解析，会把 stream 字段当成 PCM |

用 `version` 作为"能力标记"：接收端 ≥2 才保证能解析变长包。因此

- **新 PC + 旧 APK = 完全没声音**（且手机端界面看不出异常，因为包在解析前就被丢了）。
  PC 侧在收到 `version < 2` 的回报时会显著告警，提示重装 APK。
- 旧 PC + 新 APK 正常：旧 PC 只发 240 帧整包，新 APK 按长度推导出 240 帧照常处理。
