
### 2.2 路径 A（IAudioClient3 环回小周期）：**不可用**

在 VB-Cable（44.1 k）与 HDMI（48 k）两个端点上分别实测：

```
路径 A 失败：InitializeSharedAudioStream(loopback, 441f): 0x88890021 (AUDCLNT_E_INVALID_STREAM_FLAG)，回退普通 IAudioClient
路径 A 失败：InitializeSharedAudioStream(loopback, 480f): 0x88890021 (AUDCLNT_E_INVALID_STREAM_FLAG)，回退普通 IAudioClient
```

与方案书预警的错误码**完全一致**。程序按设计自动回退到普通 `IAudioClient`，功能不受影响。

### 2.3 路径 B（保活流请求最小周期）：**虚拟卡与 HDMI 无效，板载声卡有效**

初测结论是"接口成功但拿不到更小周期"——那只对当时试的两个端点成立。
后来补测板载 HD Audio 端点，路径 B 实际把环回投递粒度从 480 帧拉到 128 帧（2.67 ms），
详见 [§2.9 (1)](#29-外部评审驱动的第二轮调优pc-可验证部分已实测)。

```
保活流/路径B: IAudioClient3 渲染小周期 (路径 B) | 引擎周期 10.00ms (default 441f / min 441f) | 缓冲 970f
保活流/路径B: IAudioClient3 渲染小周期 (路径 B) | 引擎周期 10.00ms (default 480f / min 480f) | 缓冲 1056f
```

`min == default`——这两个端点（含一台虚拟声卡）根本没有更小的引擎周期可请求。
**结论：本机只能走方案书的兜底分支，接受 10 ms 引擎周期。**

- 每个回调**恰好 441 帧**（一个完整引擎周期），说明引擎按周期成批投递，`hnsBufferDuration=0` 拿到的
  22 ms 缓冲没有变成额外投递延迟；

  （不是代码里假装播放）。

48 k 端点（HDMI）同样通过：317 回调 × 480 帧 = 152160 帧，峰值 0.235。

### 2.6 5 分钟浸泡（指标是连续性，不是“能出声”）

```
$ EchoLink.Diagnostics echo --seconds 300 --quiet true
收包统计：包 60196，字节 58751296，畸形 0，
  序号跳变 0，累计采样数跳变 0，
  非零采样 55198，峰值 0.235，回报已发 2909，
  到达间隔 P50 0.75ms / P90 10.25ms / P99 10.25ms / 最大 72.90ms，
  实际速率 199.7 包/秒
结果: OK
```

- 60095 发出 / 60196 收到，**零丢包、零乱序、零畸形**，连续 300 s；
- 速率 199.7 包/秒（理论 200）；
- P99 到达间隔 10.25 ms = 引擎周期，符合预期；
- 最大 72.90 ms 是一次调度毛刺（300 s 内出现 1 次），按方案“看 P99 不看均值”的口径可以接受，
  但它提醒 32 ms 名义延迟的设备上仍可能偶发几十毫秒的尾延迟。

> **诚实记录**：第一次跑这个浸泡是 `结果: FAIL`（序号跳变 17797、速率 122 包/秒）。
> 排查结论是**诊断工具自身**的瓶颈——每个包都对全部到达间隔做一次全量排序来生成回报，
> 且每包都回一次 40 B 回报，导致接收线程把自己堵死、内核缓冲溢出。
> 改成“定长直方图 + 100 ms 节流回报 + 4 MB 接收缓冲”后，同一台机器同一份引擎代码跑出上面的通过结果。
> 引擎侧 `包/秒` 在故障期间一直是 200.0，与这个结论一致。

### 2.7 真机反馈驱动的调优（PHJ110，待复测）

2026-11-07 真机首测（设备 **PHJ110**）的现象：

| 观察 | 数值 |
| --- | --- |
| 是否能出声 | 能 |
| 欠载次数 | **2475**（极度严重） |
| 共享模式 | 未拿到独占，回退 Shared |
| burst | 256 帧（5.33 ms） |

**定位到三个独立缺陷叠加**：

1. AAudio 默认只给约 2 个 burst 的内部缓冲（≈10.7 ms），而 PC 端按 **10 ms 引擎周期成批**发包
   ——缓冲正好卡在两批之间被读空；
2. 水位下限只有 10 ms，小于一个完整发包间隔，环缓冲本身也不足以跨过批次间隙；
3. **目标水位从来没有被真正垫起来**——这一条才是 2475 次欠载的直接原因，见下面这张现场图的数据。

真机截图的硬证据（旧版本）：

| 指标 | 读数 | 含义 |
| --- | --- | --- |
| 当前水位 | **10.19 ms** | 恒在临界点，不随目标变化 |
| 目标水位 | 22.17 ms | 被欠载一次次顶高，但**实际水位不跟** |
| 欠载 | 2475 次 | 但补静音仅 625862 帧 ÷ 41394 回调 ≈ **每次只差 15 帧（0.3 ms）** |
| 日志 | 18.8 → 24.2 → 29.5 → … → 40.5 ms | 目标被反复抬高又缓慢收回，水位纹丝不动 |
| 回调最大间隔 | 150.35 ms | 由下面的路由事件刷屏触发了一次多余重开 |

**为什么水位停在 10 ms**：消费端从第 0 帧就开始读，水位会收敛到“刚好够一次回调”的临界值
（≈ 一次回调 256 帧 + 抖动），而不是目标值。目标水位当时只被用于**比较**（算比率、判丢帧），
没有任何机制把真实水位垫到那个高度。所以单纯抬高下限/加大缓冲都无效——**必须先把水位垫起来**。

**五个改动**：

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | Oboe 内部缓冲强制 ≥4 burst 且 ≥20 ms：共享模式先 `setBufferCapacityInFrames(1024)`，开流后 `setBufferSizeInFrames(max(4×burst, 20ms))`；容量提示只对共享模式设置（避免把独占顶掉） | `audio_engine.cpp` |
| 2 | 水位下限 10 → **20 ms**，并叠加 `Oboe 缓冲 × 1.15` 的动态下限（PHJ110 ≈ 24.5 ms）；缓冲变大时下限**立刻**生效 | `LatencyController.kt` |
| 3 | 独占排查：三级开流链 独占@48k → 独占@设备原生率 → 共享@48k，每级 `openStream` 的 Result 码都写 logcat 并回传 UI；显式 `setFormat(I16)` + `setSampleRate` | `audio_engine.cpp` |
| 4 | **启动垫水位**：开流/重建后先输出静音、**不消费**，直到环里攒够 target 帧才开始读；垫水位期间的静音单独计数、不算欠载（断流重建后同样重新垫） | `audio_engine.cpp` `readFrames` |
| 5 | 路由事件去重：`AudioDeviceCallback` 按“输出设备集合签名”去重 + 2 s 限流（PHJ110 上一次变化连发 12 条，每次都会触发重开） | `AudioRouteMonitor.kt` |

新增可观测项（native → UI）：`bufferSizeFrames`、`bufferCapacityFrames`、`openResult`、
`openAttempts`、`exclusiveDeniedCode`、`prefillFrames`。手机界面现在能直接看到
**Oboe 缓冲 X 帧 / Y ms**、**独占失败 code=N**、**开流尝试 N 次**、**启动垫水位 N 帧**。

单元测试：`LatencyControllerTest` 12 项（新增 2 项覆盖动态下限），全项目 **21 项通过**。

**延迟代价（必须说清楚）**：手机侧现在是「环水位 ≈24.5 ms」+「Oboe 缓冲 ≈21.3 ms」两级缓冲串联，
加上 PC 侧约 15 ms，端到端预计落到 **65–85 ms**，比原 50–70 ms 工作点上沿略高。
这是用延迟换零欠载的显式取舍；若之后要压回 50–70 ms，优先级是：
① PC 端拿到更小引擎周期（需驱动支持，本机不可用）→ ② Oboe 降到 3 burst → ③ 再调水位。

**待复测**（重装 APK 后看四件事）：

1. **当前水位**是否真的抬到了目标附近（预期 24–26 ms，而不是卡在 10 ms）——这是 2475 次欠载的根因；
2. **欠载次数**是否归零（或降到个位数且能自愈）；
3. 「开流尝试」是 1 / 2 / 3——若是 2 说明设备原生率不是 48k，独占其实拿到了；
4. 「独占失败 code=」具体是多少（预期 `-889` Unavailable 或 `-898` Unimplemented 附近），
   这决定了 PHJ110 是"系统不给"还是"参数不匹配"。

另外关注：`启动垫水位` 应是一次性的（几百到一千多帧，之后不再增长）；`回调最大间隔` 不应再出现 150 ms 这种值。

### 2.8 PC 端重启后手机端静默（已修，待复测）

PC 端 UI 换成 WPF 后在真机上复现的一个 bug，现象很有欺骗性：

| PC 界面显示的「手机回报」 | 值 | 说明 |
| --- | --- | --- |
| 丢包 | **0** | 手机自报没丢包 |
| 当前水位 | **0 ms** | 但环形缓冲是空的 |
| 目标水位 | 60 ms | 被欠载顶到上限 |
| 欠载次数 | 3487 | 约 500 次/秒 |

**"丢包 0 但水位 0"** 这组矛盾的读数说明：包都收到了，但一个都没进环。

根因：PC 端引擎每次重启，`sampleCount` 都从 0 重新计数；而手机端 `_expectedRef` 还停在上一轮
（数万）。`pushFrames` 原先把"整包落在已写区间内"一律当成重复包/乱序丢弃——**只处理了向前跳，
没处理向后退**。于是手机端要空转到 PC 端计数追上来（几分钟）才恢复，期间完全没声音。

修复（`audio_engine.cpp` `pushFrames`）：当落后超过一个最大缺口（200 ms）时，判定为发送端重启，
清空环形缓冲、把读位置归零、重新垫水位；仍然保留"小幅落后 = 重复包"的原有语义。

**待复测**：需要重装 APK（本机 adb 仍看不到设备），复测步骤：PC 端启动 → 停止 → 再启动，
手机端应在一秒内恢复出声，且「欠载」不再暴涨。

### 2.9 外部评审驱动的第二轮调优（PC 可验证部分已实测）

把实现说明交给外部模型评审后，收到的意见里有三条是**对的、且推翻了我此前的结论**。
这一节记录验证结果。

#### (1) 端点选错导致"10 ms 不可突破"——已推翻

之前只测了 VB-Cable 与 HDMI，两条路径都拿不到小周期，于是写下"本机没有更小周期可用"。
新增只读探测 `periods` 子命令后发现**板载 HD Audio 端点可以**：

```
$ EchoLink.Diagnostics periods
  入梦扬声器 (VB-Audio Cable A):        default 441f (10.00 ms), min 441f
  Virtual Speakers (AudioRelay):        default 480f (10.00 ms), min 480f
  Digital Audio (S/PDIF) (HD Audio):    default 480f (10.00 ms), min 128f (2.67 ms) ← 支持小周期
  4 - HDMI (AMD HD Audio):              default 480f (10.00 ms), min 480f
```

在 S/PDIF 上实测路径 A：仍然 `0x88890021`（环回标志全线不支持，此结论不变）；
但**路径 B 生效**——保活流拿到 2.67 ms 引擎周期后，环回投递粒度从 480 帧变成 **128 帧**。

| 端点 | 到达间隔 P50 / P90 / P99 | 形态 |
| --- | --- | --- |
| HDMI（10 ms 周期） | 0.75 / 10.25 / 10.25 ms | 每 10 ms 成对爆发（锯齿） |
| S/PDIF（2.67 ms 周期） | 5.50 / 5.50 / 5.50 ms | 均匀 |

顺带修正一处**误导性显示**：UI 原来报"请求的引擎周期"（10 ms），而实际投递是 2.67 ms。
现在报**实测的每回调帧数**，并直接在下拉框里标出各端点的最小周期。

#### (2) 名义时间戳把 PC 侧批处理延迟灌进了控制量——已改并量化

时间戳从 `sampleCount × 1000/48`（名义）改成 `sendto` 时刻的 QPC 微秒。
诊断工具同时算两套 `|dᵢ| = |Δ到达 − Δ时间戳|`，一次运行即可对比：

| 端点 | 真实发送时刻 P50/P90/P99 | 旧名义时间戳 P50/P90/P99 |
| --- | --- | --- |
| S/PDIF | 0.25 / 0.25 / 0.25 ms | 0.50 / 2.50 / 2.50 ms |
| HDMI | 0.25 / 0.25 / 0.25 ms | 5.00 / 5.25 / 5.25 ms |

旧实现把 2.5–5.25 ms 的 PC 批处理抖动当成了"链路抖动"，而目标水位正是拿它算的
（`P99 + 5 ms`）——**重复计了一次 PC 侧延迟**，目标水位因此偏大。

#### (3) Oboe 4 个 burst 没有依据——已改回 2 个

AAudio 保证回调尺寸 ≤ burst，不存在"一次回调取整个缓冲"的情况。
PHJ110 上 burst = 256 帧，4 burst ≈ 21.3 ms 白白加在端到端里。
现改为 2 burst 起步，欠载时按 burst 递增到 4（LatencyTuner 简化版），
并把 `maxCallbackFrames` 暴露到 UI 供当场证伪。

#### (4) 控制量从"平均值"改成"窗口最小值"——已改

原实现对瞬时水位做一阶低通。问题：水位是锯齿，均值必然高估半个批次（约 5 ms）；
且 20 Hz 控制周期正好是 10 ms 批的整数倍，采样相位被锁死，两端时钟漂移时会出现慢拍。
现在原生侧每次回调记录水位最小值（读-改-写区间最小值），控制线程再取 1 秒窗口的最小值作为控制量，
目标改为物理量 `burst + 5 ms`，抖动只做展示。

同时解除了"环水位 ≥ Oboe 缓冲 × 1.15"这个没有物理依据的耦合（两级缓冲吸收的是不同抖动来源）。

### 2.10 第三轮：缓冲归属修正与变长包

第二轮之后把实现再交给评审，被指出**我把缓冲的归属说反了**，同时给出三条可验证建议。

#### (1) 归属修正：Oboe 缓冲挡的是回调迟到，不是环

我原先写"环水位挡回调迟到"。这是错的：**回调迟到时网络线程照常往环里写，环水位只会涨**；
真正被抽干的是 Oboe 缓冲——HAL 没数据可读就 xrun。正确分工：

| 缓冲 | 吸收的抖动 | 该怎么定 |
| --- | --- | --- |
| 环水位 | 数据**到达**的停顿（网络、PC 侧停顿） | 水位窗口最小值，目标 = `burst + 5 ms` |
| Oboe 缓冲 | **回调间隔**的最大值（调度迟到） | 按观测到的回调间隔峰值决定 |

实现上把缓冲增长策略从"等欠载发生"改成"回调间隔峰值逼近缓冲就提前加"，
并复用已有的 `maxCallbackGapMs`（索引 18）作为判据。

#### (2) 停顿归因：原先的结论没有依据

评审指出：`d` 用真实发送时刻后，PC 侧发送停顿会同时放大 `Δ到达` 与 `Δ时间戳`、
在差分里抵消，所以 `d = 10.3 ms` 反而说明延迟发生在 `sendto` **之后**。

更关键的是——**我那次测量的接收端跑在同一台机器上**（localhost 回环），
`d` 里混着本机接收线程的调度，根本不能用来判断"PC 侧还是手机侧"。
现在改为同时输出两侧的量，真机上分别看：

- **最大发送间隔**（新增，PC 侧）：放大说明 PC 线程/引擎卡了
- **到达间隔 + `|dᵢ|`**（手机侧）：只在到达侧放大说明 `sendto` 之后有问题

#### (3) 欠载后不再一律重垫水位

停顿型欠载（数据晚到但没丢）会把环自己补满，此时重垫水位等于**多加一段静音**。
改为欠载后等 50 ms 复查：水位仍低于目标一半才重垫，否则交给丢帧迟滞/比率消化。

#### (4) 变长包：跟随抓取粒度

改成每次抓取回调发一个包（不再固定 240 帧），实测：

| 端点 | 包长 | 包率 | 到达间隔 P50/P90/P99 |
| --- | --- | --- | --- |
| S/PDIF（2.67 ms） | 128 帧 / 528 B | **373.1 包/秒** | **2.75 / 3.00 / 3.50 ms** |
| HDMI（10 ms） | 240 帧 / 976 B（拆整包） | 196.7 包/秒 | 0.75 / 10.25 / 10.25 ms |

S/PDIF 上到达间隔从 5.50 ms 降到 2.75 ms，30 秒连续性检查零畸形、零序号跳变、零采样数跳变。

**这是不兼容的线格式变更**：包长不再固定，收端必须按数据报长度推导帧数
（`(len − 16) / 4`，要求整帧且 ≤240）。旧接收端会把非 976 B 的包判成畸形丢弃，
所以已同步更新 [protocol.md](protocol.md) §1/§2/§5，并新增 `PacketLengthTest`（7 项）
覆盖 1–240 帧全部长度与三类畸形输入。

### 2.11 端到端延迟显示（新增，是估算不是实测）

之前 PC 界面上有两个"延迟"，**都不是端到端**，而且其中一个还是错的：

| 旧显示 | 实际含义 | 问题 |
| --- | --- | --- |
| 名义延迟 32.0 ms | `引擎周期 + 抓取缓冲`（10 + 22） | 只有 PC 抓取侧；用了**请求**周期而非实测 2.67 ms；还把 22 ms 抓取缓冲算进延迟，但我们每次回调都把可用数据读空，缓冲并不构成延迟 |
| 手机回报·输出延迟 33 ms | 手机 `calculateLatencyMillis` | 只有 Oboe/HAL 一层，不含环水位、网络、PC |

改为两个数字：

```
PC 抓取 = 实测抓取周期 / 2                      （S/PDIF：2.67/2 = 1.33 ms）
端到端（估） = PC 抓取 + 环水位 + 手机输出延迟
```

- **不含单向网络延迟**：两端无时钟同步，量不出来；USB 上约 1 ms，量级可忽略
- 首次报告时用估算值，**真机必须用三设备录音法校准**（[testing.md](testing.md)），
  两者差值就是"系统不可见的那部分"（DSP / 功放 / 厂商音效）

验证方式：本机起一个回报用的 sink（`sink --reply true`），让 App 发往 127.0.0.1，
sink 按协议回 40 B 状态包（水位 20 / 输出延迟 20），界面显示 **41 ms = 1.3 + 20 + 20**，
绑定与算术一致。同时也顺带验证了变长包之后回报链路仍然通（App 侧 374.8 包/秒）。

旧的 `NominalLatencyMs` 字段已从 Core 删除——它的公式是错的，留着只会被后面的人当延迟读。

### 2.12 端到端延迟首次实测：平均 45 ms（共享模式）

PHJ110 上（独占被拒，走共享模式）实测**端到端平均 45 ms**。

把 45 ms 按可见项拆开（PC 侧为实测/半周期，其余取自手机回报）：

| 环节 | 量级 | 依据 |
| --- | --- | --- |
| PC 抓取 + 打包 + USB 单向 | **≈4 ms** | 抓取半周期 1.33 + 包内平均等待 1.33 + USB ≈1 |
| 环水位 | **≈15 ms** | 最小值目标 10.33 ms，均值略高 |
| 手机输出路径（Oboe + AudioFlinger + DAC） | **≈26 ms** | 45 − 4 − 15 |

**这条算术目前只能说"大致闭合"，不能精确归因**，原因有两个：

1. 手机回报里的 `输出延迟`（`calculateLatencyMillis`）**已经包含 AudioFlinger 层**，
   它和"我们估算的 Oboe 缓冲 5.3 ms"不是一回事。此前分项表里只按 Oboe 缓冲估，
   低估了手机侧输出路径——例如 4 burst 时期那张真机截图显示 `输出延迟 33 ms`，
   远高于当时估算的 21 ms 缓冲。
2. 45 ms 的测量时刻与读数时刻未必同步，水位本身在 ±3 ms 内波动。

**可靠的部分**：手机输出路径（26 ms）确实是当前最大单项，而它主要由共享模式的
AudioFlinger 混音层贡献。水位从 15 ms 压到 8 ms 只能省 7 ms；**拿不到独占，
端到端很难低于约 38 ms**。

#### 待复测：在校准公式下扫水位

单点平均值区分不了固定开销和随水位变化的部分。用手机回报的两个数做校准：

```
固定开销 ≈ 实测端到端 − 环水位 − 输出延迟 − PC 侧(≈4 ms)
```

然后扫三档手动目标（12 / 20 / 30 ms）各测一次：

- 端到端随水位 1:1 变化 → 瓶颈在可见部分，继续压水位有效
- 端到端几乎不随水位变 → 固定开销占大头，必须动独占

同时需要手机端三个读数：**独占失败码**、**水位最低值**、**回调间隔峰值**。

### 2.13 长时浸泡与第二台设备（用户实测）

| 项 | 结果 |
| --- | --- |
| 连续运行 | **3 小时内声音始终正常、未中断** |
| 第二台设备 | 通过，延迟与 PHJ110 相当（具体读数和型号未记录） |
| 传输方式 | USB 网络共享 |

**3 小时这个时长比它听起来更有价值**：两端时钟不同源，晶振差按 ±50–100 ppm 算，
3 小时会累积 **0.5–1 秒**的相对偏移。如果重采样闭环不工作，这么长的时间足够让
水位单调抽干或单调堆积——表现就是几十分钟后开始周期性欠载，或者积压丢帧越来越多。
没有出现这些现象，说明闭环确实把漂移吃掉了。

量级估算：闭环比率上限 ±0.1%（±1000 ppm）是典型晶振偏差的 10–20 倍，
所以稳态只用到比率能力的一小部分，离饱和很远。

**这条结果排除的故障面比"没崩"宽得多。** 连续 3 小时能一直正常出声，意味着：

- PC 抓取没有停（保活流 + 环回一直有数据）
- UDP 没有断流，手机端环形缓冲没有抽干——否则会听到静音洞或断续
- 加固逻辑没有误触发重开流（错误回调 / 停摆检测 / 路由变化任一误判都会造成可闻中断）
- 没有缓慢累积的漂移把水位吃掉：3 小时累积 0.5–1 秒偏移，闭环不工作会早暴露

**缺少的是读数，不是可用性**。这次没有记录重采样比率、水位最低值和 Oboe 缓冲的趋势，
所以能写"3 小时连续可用"，暂时写不了"比率从 X 收敛到 Y"这种对比表条目。

要把它升级成"收敛"，只差一组趋势读数：

- 重采样比率应长期在 1.0 附近小幅波动，**不应贴住 ±0.1% 上限**
- 水位最低值应稳定在目标附近，**不应缓慢爬升或缓慢下降**
- Oboe 缓冲应一直停在 2 burst，**不应随时间被抬到 3/4**
- 欠载计数应始终为 0

**待补**：第二台设备的型号、是否拿到独占、burst 大小、其端到端读数；
以及两台设备在 3 小时前后各截一次图，用于对比趋势。

#### 真机复测结果（已完成）

| 待验项 | 结果 |
| --- | --- |
| `回调帧数上限` ≤ burst | ✅ **256 帧**，与 burst 相等，"回调可能一次取整个缓冲"的假设被彻底证伪 |
| `Oboe 缓冲` 是否 2 burst | ⚠️ 曾被开流空档顶到 4 burst（已修，见 §2.10），修后读数待补 |
| 欠载是否保持 0、日志是否刷屏 | ✅ 3 小时内声音未中断，未观察到刷屏 |
| 端到端 | ✅ 平均 **45 ms**（共享模式），见 §2.12 |

仍缺的读数：`水位最低值` 的稳态值、`重采样比率` 是否贴住 ±0.1% 上限、
修正后长时间运行里缓冲是否回到并稳定在 2 burst。

### 2.14 第四轮：目标水位棘轮、MMAP 定性与轨迹日志（v0.2.1）

评审指出 45 ms 里约 26 ms 卡在手机输出路径，并纠正了我两处误解
（`setMMapPolicy` 不存在；"降到 AudioTrack" 不是新路径）。按建议做了三件事。

#### (1) 目标水位加衰减——预期省约 7 ms

原实现每次欠载 `目标 += 1 burst`，**没有回落路径**。真机观察到目标从 10.3 ms 爬到 17.3 ms
后停住，而那次欠载早已结束，等于白付 7 ms——比变长包省下的 2 ms 还多。

改成"缺口 + 2 ms"的棘轮，累计上限 +10 ms，保持 60 s 后 0.1 ms/s 衰减。
同时去掉"≥2 次才抬"的门槛：有衰减退场就不需要门槛。
单元测试覆盖：抬升量按缺口而非整 burst、上限 +10 ms、保持期内不衰减、超时后衰减。

**待验证**：真机上目标是否回到 ~10.3 ms 且欠载仍为 0。

#### (2) MMAP 定性（只记录，不改行为）

开流时记录三项 + 两个系统属性：

```
mmap: supported=? enabled=? used=? | props[policy=? exclusive=?]
```

- 两项支持位都为 false → 设备不提供，应用侧无解，**不再盲试 Usage 组合**
- 支持但 `used=false` → 落到普通混音器，去 logcat 搜 `FAST denied`
  （普通混音器周期按 ≥20 ms 取整，可能是 26 ms 偏大的原因，属推测）

手机界面新增「MMAP」一行：正在使用 / 支持但未使用 / 设备不支持。

#### (3) 轨迹日志

每 10 秒一行 CSV，写到 `<应用私有目录>/files/logs/trace-<时间>.csv`：

```
elapsedSec,waterMinMs,waterAvgMs,ratio,targetMs,bufferBursts,underruns,outputLatencyMs,schedGapMaxMs
```

用途是让"收敛"可判定——3 小时没断音只证明没坏，趋势才能证明闭环在工作。启动时日志里会打印路径。

#### 一处我说错的事实（已改）

我曾写"1.56 Mbit/s ≈ 700 MB/小时会吃掉流量套餐"。**错的**：USB 共享时音频包的目的地是
手机本机地址，在手机内部终结，不进蜂窝网络；Wi-Fi 局域网同理。
真正的代价是耗电与空口占用，不是流量。
