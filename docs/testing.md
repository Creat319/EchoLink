# 验证清单与测试方法

按方案书的阶段顺序组织。每条都写清“怎么做 / 看哪个数 / 通过标准”。
**所有延迟结论都看 P50/P99，不看均值。**

---

## 1. 阶段 0：链路连通（不追求低延迟）

目的：确认“USB 共享、IP 寻址、UDP 收发、播放”四个环节没有卡住。这一步不谈延迟。

| 步骤 | 命令 / 操作 | 通过标准 |
| --- | --- | --- |
| 1.1 USB 链路 | 手机开 USB 网络共享；PC 上 `Get-NetAdapter` | 出现 `Remote NDIS ...` 适配器且 Up |
| 1.2 寻址 | `EchoLink.Diagnostics.exe targets` | 该适配器评分最高，网关 = 手机 IP |
| 1.3 端点与格式 | `EchoLink.Diagnostics.exe devices` | 列出渲染端点，混音格式正常 |
| 1.4 环回抓取 | `EchoLink.Diagnostics.exe capture --device "Cable" --seconds 5` | `结果: OK`，WAV 峰值 > 0.01 |
| 1.5 PC 端到端 | `EchoLink.Diagnostics.exe echo --seconds 8` | `结果: OK`，畸形 0、序号跳变 0、采样数跳变 0 |
| 1.6 手机收 | `EchoLink.Diagnostics.exe send --to <手机IP> --seconds 5` | 手机界面「收包」持续增长、“发送端”显示 PC 地址 |
| 1.7 出声 | PC 端播测试音 | 手机能听到 1 kHz |

> 1.5 是**不需要手机**的 PC 侧自检：引擎 → 127.0.0.1 → 本机 sink，同时验证回报通道。
> 它就是后面浸泡测试的同一套工具。

---

## 2. 阶段 1：压低延迟（记录实测参数）

目的：把每台设备的真实播放路径记下来，作为后续判断“抖动是链路的还是设备的”的基线。

在手机界面「播放链路（Oboe / AAudio）」卡里逐项抄下来：

| 字段 | 说明 | 期望 |
| --- | --- | --- |
| 采样率 | 实际流采样率 | 48000（不是则看「参数核对」卡的校正倍率） |
| burst | `getFramesPerBurst()` | 设备越好好越接近 96–192 帧 |
| 共享模式 | 独占 / 共享 | 尽量独占；回退共享约 +6 ms |
| 输出延迟 | `calculateLatencyMillis` | 与 burst 同量级 |
| 开流代数 | 每次重开 +1 | 稳定运行时应为 1 |
| 回调最大间隔 | 见下 | < 50 ms |

PC 侧对应字段（EchoLink.App「实时状态」）：

| 字段 | 期望 | 说明 |
| --- | --- | --- |
| 抓取模式 | `IAudioClient 共享模式环回 (兜底)` | 若显示 `路径 A` 说明该驱动支持小周期 |
| 引擎周期 | 10.00 ms（本机） | 决定 PC 侧抓取延迟下限 |
| 每回调帧数 | 441 或 480（整周期） | 说明引擎按周期成批投递 |
| 名义延迟 | 引擎周期 + 缓冲 | 本机约 32 ms |
| 包/秒 | 200.0 ± 0.2 | 低于 199 说明发送线程被抢占 |

**通过标准**：手机端连续出声、无断续，`开流代数` 不再增长，`包/秒` 稳定 200。

## 3. 端到端延迟测量（三设备法）

这是唯一可信的延迟测量方式——**不要相信任何单端口径的数字**。

准备：

1. PC 端把输出设备设为**能出声的端点**（或者用 VB-Cable 的 CABLE Output 作为参考录音源）；
2. PC 端点击「点击声串（10 次）」：每次 2 ms 的 2 kHz 短音，间隔 1 s；
3. 第三台设备（另一部手机/录音机）**同时**录：
   - PC 喇叭（或用声卡录音端的 CABLE Output）
   - 手机喇叭（EchoLink 接收端）
4. 把两轨对齐到同一时间轴，量每一声在两个轨上的起点差。

Audacity 操作：导入两轨 → 全选放大到每个 click → 用「光标位置」读两个起点 → 差值即端到端延迟。
10 次得到 10 个样本；跑 3 轮（间隔几分钟）得到 30 个样本。

统计：

```
P50 = 第 15 个（排序后）   P99 ≈ 最大值（样本 <100 时直接取最大，并注明样本数）
```

**通过标准**：P99 ≤ 70 ms（工作点 50–70 ms）。40–55 ms 属乐观值，不作为承诺。

记录模板：

| 轮次 | 设备 | 播放路径 | burst | 端到端 P50 | P99 | 最大 |

## 4. 浸泡测试（2 小时）

目的：验证“水位收敛”，不是验证“能出声”。

步骤：

1. 正常连上，让音乐/视频连续播放；
2. 打开手机界面，关注「水位闭环」卡的水位曲线；
3. 2 小时后记录：

| 指标 | 通过标准 |
| --- | --- |
| 水位曲线 | 贴着目标上下小幅波动，**没有单向漂移**（不缓慢爬升、不缓慢归零） |
| 重采样比率 | 长期均值略偏一侧是正常的（两晶振差），但不应持续顶在 ±0.1% |
| 欠载次数 | 应为 0；偶发个位数可接受，且之后应自行收敛 |
| 积压丢帧 | 应为 0 |
| 时间线重建 | 应为 0（出现说明断流 >200 ms） |
| 开流代数 | 不增长（增长说明触发了错误回调/停摆/路由变化） |
| 回调最大间隔 | < 100 ms |

PC 侧可同时用诊断工具做对照（不需要手机）：

```powershell
.\artifacts\pc\EchoLink.Diagnostics.exe echo --seconds 7200 --quiet true --out soak-2h.wav
```

它会在结束时打印包的连续性、到达间隔 P50/P90/P99 与实际速率。

**若水位不收敛**：按方案升级为「累计读写样本数 + 滤波后时间戳 + DLL」，见
[architecture.md](architecture.md) §4.4。

## 5. 干扰测试

| 场景 | 操作 | 观察 | 通过标准 |
| --- | --- | --- | --- |
| CPU 满载 | 起满核数的 `while(1)` 忙等 | 尾延迟、欠载 | P99 平滑上升不跳变，无断音 |
| 大文件拷贝 | 拷 20 GB 到 SSD | 同上 | 同上 |
| 手机息屏 | 关闭屏幕 10 分钟 | 是否继续出声、回调次数是否增长 | 持续播放，开流代数不变 |
| USB 控制器争用 | 同一控制器上插 U 盘持续读写 | 包丢失、抖动 | 无持续丢包 |
| 蓝牙耳机 | 连蓝牙耳机后重新开始 | 是否还能听到测试音 | 用户确认听到（否则就是静默重路由） |
| 拔插 USB | 拔掉再插上 | 重连行为 | 抓取线程自动重建或提示重新启动 |

## 6. 静默重路由（只能靠耳朵）

1. 首次连接时**必须**回答手机端弹出的「听到了吗？」；
2. 选「没听到」时，界面会提示检查媒体音量/输出路由/蓝牙；
3. 任何一次路由变化（插耳机、连蓝牙）之后，重新点「测试音」再确认一次。

这条没法自动化：API 层看不到“声音被送到了哪”。

## 7. 设备矩阵

至少覆盖一台 MMAP 可用设备 + 一台不可用设备。

| 设备 | SoC | Android 版本 | 独占是否拿到 | burst | 输出延迟 | 端到端 P50/P99 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| PHJ110 | 未记录 | 未记录 | ❌ 否（共享） | 256 帧 | 33 ms（4 burst 时期） | 45 ms（平均） | 3 小时浸泡通过 |
| 第二台（型号待补） | | | | | | 与 PHJ110 相当 | 通过；读数未记录 |

**目前两台都是"独占被拒"，所以 MMAP 可用机型这一格仍未覆盖。**
这直接影响结论强度：45 ms 是在共享模式下测的，而独占可能再省 10 ms 以上，
也可能在别的机型上因为 MMAP 路径不同而出现新问题（缓冲区由驱动固定、
`setBufferSizeInFrames` 返回 `ErrorUnimplemented`），这些都没验证过。

## 8. 已知测不出来的部分

- **静默重路由**：只能用首次测试音 + 用户确认（见 §6）。
- **USB 共享的链路丢包**：回报通道只在手机端统计，PC 端看到的是手机报回来的数字；
  若怀疑是回报链路本身丢了，用 `sink` 子命令在 PC 侧直接统计收包。
- **本仓库的自动化边界**：PC 侧可以全自动自检（§1.5 + §4），Android 侧只有单元测试
  （协议编解码、水位策略）能在 CI 里跑，真机行为必须人工测。
